# План добавления `logformat: raw | json` в danted

Дата: 2026-09-13.

Статус: этап 1 реализован и проверен на macOS; этапы 2–6 ещё не выполнены.
Настройка формата доступна, JSON-сериализация журналов пока не реализована.

## 1. Цель и результат

Добавить в серверный конфигурационный файл глобальную директиву
`logformat`, которая управляет форматом всех записей собственного логгера
Dante. По умолчанию сохраняется существующий текстовый формат `raw`.
При `logformat: json` журналы становятся JSON Lines, а события соединений
получают отдельные поля для аналитики без разбора текста `message`.

```conf
logformat: json
logoutput: /var/log/danted.log
errorlog: /var/log/danted-error.log
```

Выбранный подход: общий JSON-сериализатор и передача структурных данных
из мест формирования событий. Простая JSON-обёртка вокруг существующих
сообщений недостаточна: адреса, правила, причины завершения, длительность
и счётчики должны быть доступны отдельно.

Ориентировочный объём: **8–12 рабочих дней для одного разработчика**,
включая тестирование Linux/macOS. Это предварительная инженерная оценка,
а не результат реализации или измерений производительности.

## 2. Основания и карта изменений

План подготовлен по статическому анализу структуры исходников, вызовов
журналирования по проекту, конфигурационного парсера, распространения
конфигурации между процессами и существующего CI. При подготовке плана
сборка и runtime-тесты не запускались.

записей и отдельные ограничения сигнального пути.

## 3. Зафиксированные решения и границы

### Конфигурация

- Директива доступна только в глобальной части серверного конфига.
- Допустимые значения: `raw` и `json`; значение по умолчанию — `raw`.
- Неизвестное значение и повторная директива являются ошибками конфигурации.
- Формат един для `logoutput` и `errorlog`, включая файлы, stdout/stderr
  и содержимое сообщения, передаваемого в syslog.
- Выбор событий через правила, уровни важности и маршрутизация по получателям
  сохраняются. Включение JSON само по себе не включает дополнительные события.
- Raw сохраняет существующие сообщения и их оформление.
- Клиентские библиотеки и клиентский конфиг не получают новую настройку.
- CLI-вывод справки и версии остаётся существующим; это не записи логгера.

### Первый запуск и SIGHUP

- При первом запуске до чтения `logformat` действует raw. Директиву
  рекомендуется размещать первой, чтобы последующая диагностика была JSON.
- Предварительное отдельное чтение формата до основного парсера не добавляется.
- При SIGHUP до чтения новой директивы действует прежний формат; прочитанное
  корректное значение переключает формат в процессе, выполняющем разбор.
- Если директива отсутствует, после успешного разбора устанавливается raw.
- Дочерние процессы получают значение существующим механизмом обновления
  конфигурации через shared memory.
- Обновление процессов асинхронное: при переходе допустимо временное смешение
  raw и JSON в одном получателе.
- Существующая обработка ошибок перечитывания сохраняется. Транзакционный
  rollback всей конфигурации не входит в работу.

### Вне этой версии

- Сквозной идентификатор сессии между процессами.
- Структурирование каждого произвольного диагностического сообщения.
- Преобразование платформозависимого текста TCP_INFO в числовую схему.
- Новый формат statistics API или новые метрики этого API.
- Новая runtime-зависимость на JSON-библиотеку.
- Изменение внешнего оформления и политики хранения syslog-сервиса.

## 4. Контракт JSON

### 4.1. Общие поля и транспорт

В файлах и stdout/stderr одна запись — один JSON-объект с одним завершающим
переводом строки. Вложенные переводы строк экранируются. Текстовый raw-префикс
перед объектом отсутствует.

В syslog передаётся JSON-объект без текстового префикса Dante. Внешний syslog
заголовок добавляется системным сервисом; его файл целиком не обязан быть
JSON Lines. Уровень и facility продолжают передаваться существующим способом.

| Поле | Тип | Смысл |
|---|---|---|
| `schema_version` | integer | Версия схемы, первоначально `1` |
| `timestamp` | string | Unix time в виде `seconds.microseconds`, ровно шесть цифр после точки |
| `level` | string | Текстовый уровень важности |
| `pid` | integer | PID процесса, создавшего запись |
| `process` | string | Роль процесса |
| `program` | string | Имя программы |
| `event` | string | Тип события; `message` для общей диагностики |
| `message` | string | Человекочитаемое сообщение без стандартного raw-префикса |
| `truncated` | boolean | Признак усечения при формировании JSON-записи |

Иллюстрация общей диагностической записи; пример записан одной строкой:

```json
{"schema_version":1,"timestamp":"1789257600.123456","level":"info","pid":1234,"process":"mother","program":"danted","event":"message","message":"server ready","truncated":false}
```

`truncated` отражает усечение, обнаруженное при построении события и JSON.
Он не может обнаруживать изменение записи внешним syslog-сервисом.

### 4.2. Структурные события соединений

Для операций `iolog()` выделяются типы событий:

- `accept`, `hostid`, `connect`;
- `block`, `temporary_block`;
- `disconnect`, `error`, `temporary_error`;
- `io`.

Доступные поля передаются из исходных C-структур, без разбора готовых
строк журналов регулярными выражениями:

- `rule.number`, `rule.type`, `verdict`, `protocol`, `command`;
- `source`, `destination`, `source_proxy`, `destination_proxy`;
- известный метод аутентификации и идентификатор пользователя;
- дополнительные данные конкретного события и известная ошибка.

Каждый адресный объект содержит доступные `local` и `peer`. Endpoint включает
тип адреса, адрес без порта и числовой порт. Представление должно поддерживать
IPv4, IPv6 и доменное имя, сохраняя различие локального и удалённого адреса
и адресов промежуточного proxy.

Блокировка правилом отличается от ошибки соединения. Текст `message`
сохраняется для человека, но не служит источником структурных полей.

Неизвестные значения опускаются; известное нулевое значение сохраняется.
Пароли и содержимое credential-структур не сериализуются. Payload включается
только при существующем разрешении `log: data`. TCP_INFO остаётся текстовым
полем с корректным экранированием.

### 4.3. Закрытие и статистические снимки

Закрытие соединения в `io_delete()` должно формировать структурное событие
с причиной завершения, стороной ошибки, известным кодом ошибки,
`duration_us`, счётчиками чтения/записи байтов на стороне client/target и
соответствующими счётчиками UDP-пакетов.

Направления счётчиков определяются с учётом BIND и существующего разворота
сторон, а не только по текущему имени `src` или `dst` в структуре.

Статистика соединений из `siginfo()` получает отдельный тип
`session_snapshot`. Снимки не должны восприниматься потребителем как новые
закрытия или дополнительные дельты трафика.

### 4.4. Сериализация и ограничения

- Экранировать кавычки, обратные слеши и управляющие символы.
- Сохранять корректный UTF-8; некорректные байты представлять через `\u00XX`.
- Для сигнального пути использовать ограниченный буфер без allocation.
- При нехватке памяти использовать ограниченный fallback, сохраняющий
  корректный JSON и выставляющий `truncated: true`.
- Усекать значения с резервом под завершающие кавычки, скобки и перевод
  строки; не обрезать готовый сериализованный объект произвольным байтом.
- Не добавлять небезопасные для обработчика сигнала зависимости и сохранять
  `errno` по существующему контракту логгера.
- Дамп отладочного кольцевого буфера выдавать одним JSON-событием с
  экранированным содержимым.
- Для pipe/FIFO ограничивать размер сформированной записи размером
  атомарной записи получателя. Учитывать этот предел до вызова записи.
- Проверять конкурентную запись workers и обработку `EINTR`/короткой записи;
  не заявлять атомарность произвольного размера для всех типов получателей.
- Корректность объекта гарантируется на выходе собственного сериализатора;
  внешнее усечение syslog-сервисом находится вне этой гарантии.

## 6. Итоговая матрица приёмки

| Область | Обязательные сценарии | Ожидаемый результат |
|---|---|---|
| Конфигурация | Отсутствие, raw, JSON, неверное/повторное значение, неверное размещение | Default raw; корректные настройки принимаются; остальные диагностируются |
| Raw-совместимость | Фиксированные время/PID, обычные и специальные сообщения | Прежнее оформление и содержание, прежние получатели и фильтры |
| JSON | Unicode, некорректный UTF-8, экранирование, multiline, длинные сообщения | Каждая сформированная строка — валидный объект, без внешнего raw-префикса |
| Ресурсные ограничения | Allocation failure, заполнение буфера, pipe/FIFO | Корректный ограниченный объект, достоверный признак усечения |
| Соединения | CONNECT, BIND, UDP ASSOCIATE, allow/block, ошибки | Поля совпадают с исходными данными события |
| Статистика | Известный трафик, закрытие, timeout, snapshots | Правильные числовые значения и направления; snapshots отличимы от закрытий |
| Специальные пути | Debug, сигналы, stack trace, ring buffer, ошибки парсера | JSON после активации формата; сохранение ограничений сигналов |
| Reload | raw ↔ JSON, удаление директивы, новые и существующие workers | Согласованная семантика переключения с допустимым переходным смешением |
| Получатели | Файл, stdout/stderr, errorlog, syslog payload | Правильное оформление, уровни и маршрутизация |
| Конкурентность | Несколько workers, длинные записи, `EINTR`/короткая запись | Отсутствие повреждения объектов в поддерживаемых условиях записи |
| Регрессии | Linux/macOS server builds, client build, statistics API и smoke tests | Сборки и существующие проверки проходят |

## 7. Завершение и внедрение

Работа завершена, когда после активации `logformat: json` все записи
собственного логгера корректно сериализуются, а соединения, причины их
завершения и итоговая статистика доступны по полям без разбора `message`.

Внедрение остаётся opt-in: обновление бинарного файла само по себе не меняет
формат журналов. Для включения администратор добавляет директиву и выполняет
перезапуск или SIGHUP. Для возврата к прежнему формату указывает `raw` либо
удаляет директиву и перечитывает конфигурацию.

При смене формата существующий лог-файл может содержать записи обоих форматов.
Потребитель должен учитывать границу переключения, а при SIGHUP — также
асинхронное обновление процессов. Ранние сообщения до чтения настройки и
внешнее оформление syslog трактуются согласно разделам 3 и 4.

Основные риски реализации: пропущенные прямые события в `sockd_io.c`,
нарушение ограничений сигнального пути, неверные направления BIND/UDP-счётчиков,
усечение объектов и регрессия raw или клиентской сборки. Для каждого из них
предусмотрены отдельные проверки в этапах и итоговой матрице.
